## 2. 이미 결정한 것 — 다시 논의하지 말 것

재개할 때 이 항목들을 "해볼까?" 하고 다시 꺼내면 시간 낭비다. 각각 **실측이나 명시적
판단으로 결론이 난 것**들이다.

### 2-1. 교차 참조 조문 자동 추가 검색 — ❌ 하지 않음 (실측으로 기각)

처벌 조문(제10조)이 검색될 때 그 본문이 인용하는 의무 조문(제9조)도 자동으로 함께
가져오자는 아이디어. **통제 실험으로 기각됐다** (#46):

- 무관한 조문을 제9조로 **교체**해 컨텍스트 5개를 유지한 상태에서 3회 판정 →
  PARTIAL 3/3으로 **전혀 바뀌지 않음**
- 코퍼스의 **54.8%(893/1,629)**가 다른 조문을 참조 → 비용은 절반 이상으로 퍼지는데
  효과는 0

진짜 원인은 판정기가 컨텍스트에 조문번호 라벨을 안 붙인 것이었고, 그건 고쳤다.

### 2-2. CI에 RAGAS/eval 붙이기 — ❌ 현재로선 하지 않음

매 커밋마다 OpenAI 비용이 나가고(월 $5 예산), 실행 시간이 9분~4시간으로 들쭉날쭉했다.
"CI 게이트는 주로 **다른 개발자가 테스트를 건너뛰는 것**을 막는 장치"인데 1인
프로젝트엔 그 전제가 없다. 체크포인트마다 수동 실행이 맞다고 판단.

⚠️ 단, **팀에 합류하거나 협업자가 생기면 이 판단은 뒤집힌다.** 그때 다시 검토.

### 2-3. Cross-Encoder Reranking — ❌ 영구 제거 (실측으로 유해 확인)

Top-1 정확도 66.7% → 13.3%로 악화. 다국어 CE도 순수 벡터 순서를 못 이겼다(#25).
다시 시도하지 말 것.

### 2-4. 면접 전 대규모 변경 — ❌ 하지 않음 (기간 한정)

baseline 수치가 흔들리면 "문서에 적힌 숫자 ≠ 지금 돌리면 나오는 숫자"가 되어 오히려
신뢰를 깎는다. **이 제약은 2026-09-14 이후 해제된다.**

## 3. 백로그 — 우선순위순

### 🔴 P1. eval 생성 단계를 프로덕션과 정렬

**문제**: `eval/retriever.py`의 `_generate()`가 프로덕션 `law_rag_tool`과 **다른 간소
프롬프트**를 쓴다. 검색 경로는 프로덕션과 맞춰놨지만(v1.6.1) 생성은 안 맞다. 즉 지금의
Faithfulness·GROUNDED 수치는 **사용자가 실제로 받는 답변을 측정한 게 아니다.**

실측 근거: PARTIAL로 남은 2건(GS-016, GS-023)을 프로덕션 `law_rag_tool.run()`으로 다시
돌리니 **둘 다 GROUNDED**였다. eval 쪽 프롬프트만의 문제였다.

**할 일**: `_generate()`를 없애고 `law_rag_tool.run()`을 호출해 스트리밍 텍스트를 모으는
방식으로 교체. 프롬프트를 두 곳에 복제하지 않게 된다.

**⚠️ 대가**: 과거 baseline이 전부 무효가 되고 `--compare` 회귀 게이트가 기준점을 잃는다
(재수립에 최소 2회 실행). 프로덕션 답변이 4개 섹션으로 더 길어서 **Faithfulness가
낮아질 가능성이 있다** — 숫자가 나빠져도 그게 더 정직한 값이라는 걸 감수할 준비가
돼 있어야 한다.

**검증**: 재정렬 후 2회 연속 실행해 새 baseline 확립 → README 수치 갱신.

### 🔴 P2. rubric 기반 구조화 채점 (새 능력)

**왜 이게 1순위 신규 기능인가**: law11의 eval 근육(골든셋·판정기·회귀 하니스)을 그대로
재사용하면서 **지금 없는 능력**을 증명한다. 기존 기능을 더 다듬는 건 이미 충분히
증명된 역량이라 새로 얻는 게 적다.

**할 일**: 항목별 rubric을 structured output으로 독립 판정 후 합산.
`{"항목명": "충족|부분충족|미충족", "근거": "...", "인용": "..."}` 형태.
`response_format={"type": "json_object"}`로 파싱 안정성 확보.

**검증**: 이것도 **골든셋을 만들어서 측정할 것.** 만들자마자 "잘 되는 것 같다"로 넘어가지
말 것 — 그게 이 프로젝트가 반복해서 피해온 실수다.

## 4. 방향 — 무엇을 증명할 것인가

지금 law11에서 "더 하드닝하기"는 한계효용이 거의 0이다. changelog 48건으로 그 역량은
이미 증명됐다. **49번째 결함을 고쳐도 새로 알려지는 게 없다.**

| law11이 증명하는 것 | 증명 못 하는 것 |
|---|---|
| 측정 기반 진단·개선 | **실제 운영 경험** (배포 없음, 사용자 0명) |
| 자기 지표까지 의심하는 검증 규율 | **협업** (전부 1인) |
| 1인 기획→배포 완주 | **트래픽·비용·지연이 실제 문제가 되는 상황** |
| 정직한 문서화 | **모델 자체를 다루는 일** (전부 API 오케스트레이션) |

**권장 순서: P2(rubric) → 운영(재배포·관측)**

P1은 P2를 하는 과정에서 자연스럽게 필요해진다(새 기능도 골든셋으로 재야 하므로).
운영을 뒤에 두는 이유는 띄울 만한 게 있어야 띄우는 의미가 있기 때문.

**대안**: 지금 "직접 해본 적 없다"고 답하는 영역(vLLM·파인튜닝·GPU 서빙)을 배우는 게
목적이라면, law11에 억지로 붙이는 것보다 **별도의 작은 프로젝트**가 낫다.
